# КР №3 — backend и web-клиент колл-центра

Реализация продолжает проект КР №1/2 из ветки `kr2-javafx`. JavaFX остаётся в корневых `src/` и `pom.xml`, новый независимый Spring Boot модуль расположен в `backend/`. Web-клиент (HTML/CSS/JavaScript без дополнительной сборки) обслуживается тем же сервером. Android в КР №4 сможет использовать JSON REST API. Это не требует запуска JavaFX.

## Быстрый запуск

Нужен Docker Desktop с запущенным engine. Java 21 и Maven для сборки находятся в Dockerfile; локально устанавливать их необязательно. Первый запуск скачивает образы и Maven-зависимости.

```sh
python3 scripts/init_env.py
docker compose --env-file .env -f backend/docker-compose.yml up -d --build --wait
```

В Windows при установленном Python используйте `python scripts/init_env.py`, затем `powershell -ExecutionPolicy Bypass -File backend/start-compose.ps1`. Если Python отсутствует, скопируйте `.env.example` в `.env` и заполните случайные секреты; JWT_SECRET_BASE64 — Base64 минимум 32 случайных байтов. Скрипт не перезаписывает существующий `.env`.

- Приложение: http://localhost:8080/
- Health: http://localhost:8080/actuator/health
- Swagger: http://localhost:8080/swagger-ui.html (после входа администратором и смены временного пароля)
- OpenAPI: http://localhost:8080/v3/api-docs (авторизация администратора)
- PostgreSQL: localhost:55432, база `call_center`.

Логин администратора указан в `.env` как BOOTSTRAP_ADMIN_EMAIL, временный пароль — BOOTSTRAP_ADMIN_PASSWORD. Секреты генерируются индивидуально, не включаются в Git. После первого входа обязательна смена пароля. В браузере refresh хранится в HttpOnly cookie, access — в памяти вкладки. Для Android передавайте `clientType: "NATIVE"`; refresh возвращается в JSON.

Проверка и остановка:

```sh
docker compose --env-file .env -f backend/docker-compose.yml ps
docker compose --env-file .env -f backend/docker-compose.yml logs --tail=100 backend
docker compose --env-file .env -f backend/docker-compose.yml down
```

`down` сохраняет именованный volume базы. `down -v` удаляет данные, для обычной остановки он не нужен. Порты опубликованы только на 127.0.0.1. Если заняты 8080 или 55432, измените APP_PORT/POSTGRES_PORT в `.env`.

## Модель и бизнес-правила

Клиент связывается по телефону с сохранённой таблицей `clients`; имя и контакты в обращении — снимок на момент обработки.

`Appeal` содержит UUID, externalId (номер), тему, клиента, контактные данные, категорию, колл-центр, оператора, статус, влияние impactScore 0..100, urgent, теги, priorityLevel, даты, version и archived. Срок решения dueDate — дополнительное необязательное поле.

Категории: TECH, COMPLAINT, CONSULTATION, BILLING. Новая запись создаётся в NEW. Переходы: NEW → IN_PROGRESS → RESOLVED → CLOSED; из IN_PROGRESS также можно перейти в ESCALATED, затем в RESOLVED. Сохранение без изменения статуса допустимо. Обратные переходы запрещены. Оператор обязателен для всех статусов кроме NEW. Неактивного оператора нельзя назначить заново. Для одного оператора допускается максимум пять неархивных обращений в NEW/IN_PROGRESS/ESCALATED; назначение блокирует строку оператора в транзакции, чтобы параллельные запросы API не превысили лимит.

Приоритет рассчитывается сервером: решённые/закрытые → NOT_APPLICABLE; urgent и влияние >=80 → CRITICAL; urgent либо влияние >=80 либо ESCALATED → HIGH; влияние >=40 → MEDIUM; иначе LOW. Клиент не может передать готовый приоритет вместо расчёта.

`CallCenter` — справочник колл-центров с кодом, названием, SLA в часах и активностью. Справочник меняет ADMIN. Операторы доступны для выбора через `/api/operators`. В web доступны разделы клиентов и операторов с поиском, страницами, карточками, созданием, изменением и удалением несвязанных записей.

Роли: VIEWER — чтение; EDITOR — обращения, заметки, CSV, массовые действия; ADMIN — также справочник, пользователи, аудит, окончательное удаление. JWT содержит короткий срок действия; актуальность пользователя и роли перечитываются из БД.

## Данные КР1/КР2 и миграции

Flyway, Hibernate `ddl-auto: validate`. Автоматическое пересоздание рабочей схемы отключено.

- V1 создаёт исходные `call_centers`, `operators`, `clients`, `appeals` без DROP.
- V2 добавляет пользователей, роли, refresh-сессии, UUID-обращения, колл-центры, теги, заметки и аудит.
- V3 переносит прежние записи в новую модель с детерминированными UUID, сохраняет ссылки на прежних операторов/клиентов и закрытые даты. Исходные таблицы не удаляются.
- V5 добавляет версии клиентам/операторам и общую UUID-связь операторов с колл-центрами.
- V4 заполняет демонстрационные данные только при отсутствии исходных колл-центров и клиентов, затем переносит их в API-таблицы.

Для переноса существующей БД КР2 сначала сделайте резервную копию и работайте с её копией. Если таблицы V1 уже существуют и Flyway history ещё нет, однократно выполните Flyway baseline версии 1, затем migrate. Через Spring Boot для этого первого запуска можно явно задать `SPRING_FLYWAY_BASELINE_ON_MIGRATE=true` и `SPRING_FLYWAY_BASELINE_VERSION=1`. Не включайте baseline для незнакомой схемы. После перехода авторитетный источник для web/Android — новые таблицы; двусторонней синхронизации с записями, которые старый JavaFX создаёт после миграции, нет.

## REST API

| Назначение | Метод / путь |
|---|---|
| Вход / обновление / выход | POST /api/auth/login, /refresh, /logout |
| Текущий пользователь | GET /api/auth/me |
| Смена временного / постоянного пароля | POST /api/auth/change-initial-password, /change-password |
| Список / карточка | GET /api/appeals, /api/appeals/{id} |
| Создание / изменение | POST /api/appeals, PUT /api/appeals/{id} |
| Архив / восстановление | DELETE /api/appeals/{id}, POST /api/appeals/{id}/restore |
| Окончательное удаление ADMIN | DELETE /api/appeals/{id}/permanent + X-Confirm-Delete: PERMANENTLY_DELETE |
| Массовая операция | POST /api/appeals/bulk |
| CSV preview / apply | POST /api/appeals/import/preview, /apply; multipart поле file, параметр mode |
| Экспорт выборки | GET /api/appeals/export?q=... |
| Заметки | GET/POST /api/appeals/{id}/notes; PUT/DELETE /api/appeals/{id}/notes/{noteId} |
| Колл-центры | GET/POST /api/centers; PUT /api/centers/{id}; PATCH /api/centers/{id}/active |
| Операторы | GET /api/operators |
| Аналитика | GET /api/analytics/summary |
| Пользователи | GET/POST /api/admin/users; PUT /api/admin/users/{id}; POST /api/admin/users/{id}/reset-password |
| Аудит | GET /api/admin/audit |

Swagger содержит точные DTO. При PUT передавайте version из последнего GET. Устаревшая версия возвращает 409, неверные данные — 400, отсутствие входа — 401, недостаток прав — 403, отсутствие записи — 404. Сущности JPA не сериализуются напрямую, ошибки содержат correlationId без stack trace.

Поиск `q`: обычный текст плюс команды, например `сеть center:CENTER-1 status:NEW urgency:true priority:high tag:сеть impact>=40 archived:all`. Русские аналоги: колл-центр, статус, срочно, приоритет, тег, влияние, архив. По умолчанию архив исключён. Числовые сравнения: <, <=, =, >=, >. Фильтры исполняются Criteria API с параметрами, пользовательский SQL не принимается. Пагинация `page=0&size=25` (максимум 100), сортировки `name`, `topic`, `center`, `status`, `impact`, `priority`, `updated` плюс `asc/desc`.

CSV UTF-8 (BOM поддерживается), разделитель запятая, теги через `|`. Заголовки и пример находятся в `examples/appeals.csv`. Preview не записывает данные. Apply повторяет валидацию, чтобы не доверять старому preview; каждую строку применяет отдельно. Режимы CREATE_ONLY и UPSERT_BY_EXTERNAL_ID. Некорректные строки не мешают корректным, результат содержит число созданных/обновлённых/пропущенных и список ошибок. Состояние БД может измениться после preview; окончательный результат сообщает apply.

## Проверка четырёх сущностей

- `CallCenter`: UUID-справочник `center`, создание/изменение/активность доступны ADMIN. Отключённый центр нельзя назначить новой записи, но существующие связанные обращения можно редактировать.
- `CallOperator`: существующая таблица `operators`, выбор через GET `/api/operators`. Проверяются наличие, активность при новом назначении и лимит пяти активных обращений. CRUD операторов доступен в разделе «Операторы», изменение — ADMIN.
- `CallClient`: существующая таблица `clients`, поиск по телефону или создание при сохранении обращения. Имя/email в обращении — снимок, изменение карточки обращения не обновляет общую запись клиента. CRUD клиентов доступен в разделе «Клиенты», создание/изменение — EDITOR и ADMIN, удаление — ADMIN.
- `Appeal`: UUID-таблица `appeal`, основной CRUD, статусы, версии, архив/восстановление, CSV, заметки и массовые операции. Связи с клиентом и оператором реализованы идентификаторами и внешними ключами БД; связь с новым справочником — JPA ManyToOne.

Миграция V5 добавляет операторам обязательный UUID `center_id`, связанный с тем же справочником `center`, что и обращения. Новые операторы могут работать в новых колл-центрах web. Старый `call_center_id` сохранён только для прежних данных КР2 и не синхронизируется при изменении через API; новые операторы не предназначены для старого JavaFX-клиента. Обоим справочникам добавлен `@Version`.

API справочников: GET/POST `/api/directory/clients` и `/api/directory/operators`; PUT/DELETE `/{id}`. GET принимает `q`, `page`, `size` (1–100), сортирует по имени и id. PUT передаёт version в JSON, DELETE — параметром запроса. Удаление клиента/оператора, на которого ссылаются новые либо старые обращения, возвращает 409. Оператора с историей можно отключить через форму редактирования. Его текущие обращения сохраняются, новые назначения запрещены. Логин оператора — атрибут сотрудника, доступ в систему отдельно управляется через «Пользователи».

Повторная проверка: исправлены изменение даты при повторном массовом CLOSED, невозможность редактировать обращение с ранее отключённым центром, лишняя проверка нагрузки для архивного редактирования и отсутствие проверки нагрузки в CSV preview. Добавлены четыре регрессионных теста; все 18 Maven-тестов и 19 групп HTTP-проверок прошли. Preview проверяет текущую нагрузку, apply повторяет проверку для каждой строки с учётом уже применённых строк.
