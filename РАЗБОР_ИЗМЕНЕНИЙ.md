# Разбор изменений: отдельные окна для сущностей

Этот файл объясняет каждое изменение в проекте: что было, что стало, зачем и как это работает. В конце есть список вопросов, которые могут задать на защите, с ответами.

---

## 0. Короткая версия (то, что надо сказать за 30 секунд)

Раньше приложение было одним окном про обращения. Клиентов, операторов и колл-центры нельзя было ни добавить, ни изменить из интерфейса, их можно было только выбрать в выпадающем списке.

Теперь при запуске открывается **главное меню** с четырьмя плитками. Каждая плитка открывает **отдельное окно** (свой `Stage`, свой FXML, свой контроллер):

| Окно | FXML | Контроллер | Форма добавления/изменения |
|---|---|---|---|
| Обращения | `main-view.fxml` | `MainController` (был) | `appeal-form.fxml` + `AppealFormController` (был) |
| Клиенты | `clients-view.fxml` | `ClientsController` | `client-form.fxml` + `ClientFormController` |
| Операторы | `operators-view.fxml` | `OperatorsController` | `operator-form.fxml` + `OperatorFormController` |
| Колл-центры | `call-centers-view.fxml` | `CallCentersController` | `call-center-form.fxml` + `CallCenterFormController` |

Если в одном окне что-то поменяли (например, переименовали клиента), все остальные открытые окна сами обновляются.

Архитектура не поменялась: `FXML → Controller → Service → Repository → PostgreSQL`. SQL по-прежнему только в репозиториях, проверки данных только в сервисах.

## 1. Что было до меня и что я проверил

У тебя в папке лежала незакоммиченная переделка «Отдел (Department) → Колл-центр (CallCenter)»:

- удалены `Department.java`, `DepartmentRepository.java`, `DepartmentService.java`;
- добавлены `CallCenter.java`, `CallCenterRepository.java`, `CallCenterService.java`;
- в `init.sql` таблица `departments` (name, description) заменена на `call_centers` (name, **address**), а у операторов колонка `department_id` стала `call_center_id`.

Я её проверил: проект собирается, все тесты проходят, включая интеграционный на настоящем PostgreSQL 16. По коду переделка была закончена, я её не трогал.

**Найденная проблема.** Docker выполняет `init.sql` только один раз, когда создаёт пустой volume `callcenter-pgdata`. Если база создавалась старой версией, в ней до сих пор таблица `departments`, а новый код ищет `call_centers`. Тогда падают список операторов и «Просмотр». Для этого добавлен скрипт миграции (раздел 6).

## 2. Как теперь запускается приложение (по шагам)

1. `mvn javafx:run` запускает `ru.mirea.callcenter.ui.App`.
2. `App.start(stage)` загружает `home-view.fxml`. Это главное меню, его контроллер `HomeController`.
3. `HomeController.initialize()` вызывает `refresh()`: читает из БД обращения, клиентов, операторов, колл-центры и пишет на плитках сводку («10 всего, не закрыто 7», «4 активных из 5» и т. д.). Если БД недоступна, внизу показывается понятная ошибка красным.
4. Нажали плитку «Клиенты»: вызывается `onClients()`, а он вызывает `WindowFactory.openWindow("clients-view.fxml", "Клиенты", 860, 560)`.
5. `openWindow` создаёт новый `Stage`, загружает FXML, показывает окно через `show()` (не `showAndWait()`, поэтому окно не блокирует остальные).
6. Если окно «Клиенты» уже открыто, второе не создаётся: старое просто выводится на передний план.
7. Закрыли главное меню: `stage.setOnCloseRequest(e -> Platform.exit())`, и закрываются все окна приложения.

## 3. Новые и изменённые файлы: слой интерфейса (`ui`)

### 3.1. `ui/App.java` (изменён)

Раньше открывал сразу таблицу обращений. Теперь открывает главное меню:

```java
FXMLLoader loader = WindowFactory.loader("home-view.fxml");
stage.setScene(WindowFactory.scene(loader.load(), 640, 460));
if (loader.getController() instanceof Refreshable home) WindowFactory.register(home);
stage.setOnCloseRequest(e -> Platform.exit());
```

- `WindowFactory.loader(...)` и `WindowFactory.scene(...)` это маленькие помощники, чтобы не повторять путь к FXML и подключение `style.css` в каждом месте.
- `instanceof Refreshable home` это сопоставление с образцом (pattern matching, Java 16+): проверка типа и приведение в одной строке.
- `register(home)` подписывает меню на обновления, чтобы цифры на плитках менялись после изменений в других окнах.

### 3.2. `ui/util/WindowFactory.java` (изменён)

Был один метод `openModal` (модальное окно). Теперь:

| Метод | Что делает |
|---|---|
| `openModal(owner, fxml, title, init)` | Как раньше: модальное окно (`Modality.WINDOW_MODAL`, `showAndWait()`). Используется для форм. Возвращает контроллер, чтобы потом спросить `isSaved()`. |
| `openWindow(fxml, title, w, h)` | **Новый.** Отдельное немодальное окно раздела. Одно окно на раздел. |
| `register(Refreshable)` | Добавляет контроллер в список тех, кого надо обновлять. |
| `refreshAll()` | Вызывает `refresh()` у всех открытых окон. |
| `loader`, `scene` | Вспомогательные: загрузчик FXML и сцена с подключённым CSS. |

Два поля:

```java
private static final Map<String, Stage> OPEN_WINDOWS = new HashMap<>();   // какие разделы открыты
private static final List<Refreshable> LISTENERS = new ArrayList<>();     // кого обновлять
```

Когда окно закрывается, `stage.setOnHidden(...)` удаляет его из обеих коллекций. Иначе мы бы обновляли закрытые окна и держали их в памяти.

`refreshAll()` проходит по `List.copyOf(LISTENERS)`, то есть по копии списка. Это защита на случай, если во время обновления список изменится (иначе `ConcurrentModificationException`).

**Модальное и немодальное окно, в чём разница.** Модальное (`WINDOW_MODAL`) блокирует окно-владелец, пока само открыто, а `showAndWait()` останавливает выполнение кода до закрытия. Поэтому после строки с `openModal` можно сразу проверить `form.isSaved()`. Немодальное (`show()`) возвращается сразу, пользователь может переключаться между окнами.

### 3.3. `ui/util/Refreshable.java` (новый)

```java
public interface Refreshable { void refresh(); }
```

Интерфейс «окно умеет перечитать данные». Его реализуют `HomeController`, `MainController`, `ClientsController`, `OperatorsController`, `CallCentersController`. Вместе с `WindowFactory.refreshAll()` это паттерн **«Наблюдатель» (Observer)**: окно, где что-то поменяли, не знает, какие ещё окна открыты, оно просто говорит «данные изменились», а все подписанные окна обновляются.

### 3.4. `ui/util/Converters.java` (новый)

`ComboBox` по умолчанию показывает `toString()` объекта, а у моделей там технический вид `1 | Центральный офис | ...`. `Converters.of(CallCenter::getName)` создаёт `StringConverter`, который показывает пользователю только нужный текст. Раньше такой же метод `converter(...)` был скопирован в `MainController` и `AppealFormController`; новые классы используют общий.

### 3.5. `ui/controller/HomeController.java` + `home-view.fxml` (новые)

Главное меню. В FXML это `GridPane` 2×2, в каждой ячейке `Button` со стилем `nav-tile`, внутри (`<graphic>`) заголовок и строка-сводка (`fx:id="clientsCount"` и т. п.).

- `refresh()` считает сводку через сервисы (`AppContext.appeals().getAll()` и т. д.) и Stream API (`filter(...).count()`).
- `onAppeals()`, `onClients()`, `onOperators()`, `onCallCenters()` открывают окна. Обёрнуты в `AlertUtil.run(...)`, поэтому любая ошибка (например, не нашёлся FXML) показывается диалогом, а не роняет программу.

### 3.6. `ui/controller/EntityListController.java` (новый, абстрактный)

Это «общий скелет» окон «Клиенты», «Операторы», «Колл-центры». Они почти одинаковые: таблица, строка поиска, кнопки «Добавить/Изменить/Удалить/Обновить». Чтобы не писать одно и то же три раза, общий код вынесен сюда, а подклассы описывают только различия.

Класс обобщённый: `EntityListController<T>`, где `T` это `Client`, `Operator` или `CallCenter`.

**Абстрактные методы (их обязан написать подкласс):**

| Метод | Зачем |
|---|---|
| `setupColumns()` | Какие столбцы и что в них показывать |
| `load()` | Загрузить записи из БД через сервис |
| `matches(item, query)` | Подходит ли запись под строку поиска |
| `idOf(item)` | id записи (нужен, чтобы вернуть выделение после обновления) |
| `countCaption()` | Подпись счётчика: «Показано клиентов» |
| `openForm(item)` | Открыть форму (null = новая запись), вернуть «сохранили или нет» |
| `deleteQuestion(item)` | Текст вопроса при удалении |
| `delete(item)` | Удалить через сервис |

Плюс два «крючка» с реализацией по умолчанию: `extraFilter(item)` (дополнительные фильтры, по умолчанию «пропустить всё») и `setupExtraFilters()`. Их переопределяют только операторы.

Это паттерн **«Шаблонный метод» (Template Method)**: базовый класс задаёт порядок действий (`initialize`, `refresh`, `onDelete`...), а отдельные шаги делегирует подклассу.

**Как устроены данные в таблице:**

```java
protected final ObservableList<T> items = FXCollections.observableArrayList(); // все записи из БД
private final FilteredList<T> filtered = new FilteredList<>(items);           // после поиска/фильтров
SortedList<T> sorted = new SortedList<>(filtered);                            // после сортировки
sorted.comparatorProperty().bind(table.comparatorProperty());                 // сортировка по клику на заголовок
table.setItems(sorted);
```

Цепочка `ObservableList → FilteredList → SortedList → TableView`. Каждый следующий список «смотрит» на предыдущий. Когда меняются `items` (загрузили из БД) или предикат фильтра (ввели текст в поиск), таблица перерисовывается сама. Поиск здесь работает в памяти, без нового запроса в БД.

`bind(table.comparatorProperty())` нужен, потому что `FilteredList` сам сортировать не умеет. Без этой строки клик по заголовку столбца не сортировал бы.

**`initialize()`:**
- кнопки «Изменить» и «Удалить» неактивны, пока ничего не выбрано: `editButton.disableProperty().bind(noSelection)`; это привязка свойств (binding);
- двойной клик по строке открывает редактирование;
- любое изменение текста поиска вызывает `applyFilter()`.

**`refresh()`:** запоминает id выбранной строки, перезагружает `items`, применяет фильтр и снова выделяет ту же запись. Без этого после каждого сохранения выделение бы слетало.

**`onAdd/onEdit/onDelete`:** после успешного действия вызывают `WindowFactory.refreshAll()`, чтобы обновились все окна, а не только текущее.

**Как `FXMLLoader` работает с наследованием.** Поля `searchField`, `table`, `infoLabel`, `editButton`, `deleteButton` объявлены в базовом классе с `@FXML`. Загрузчик ищет поля с `fx:id` по всей иерархии классов, поэтому они заполняются, хотя в `fx:controller` указан подкласс. То же для обработчиков (`onAction="#onAdd"`) и `initialize()`.

### 3.7. `ui/controller/EntityFormController.java` (новый, абстрактный)

То же самое для форм. Общее:

- `setEntity(item)`: null = «Новый клиент», иначе «Редактирование клиента» и заполнение полей;
- `onSave()`: собирает объект из полей (`build()`), сохраняет (`save(...)`), закрывает окно;
- ошибки: если сервис бросил `BusinessException` с кодом поля, это поле обводится красной рамкой (CSS-класс `field-error`) и получает фокус, а текст ошибки показывается под формой;
- любая другая ошибка (например, БД) переводится в понятный текст через `UiErrors.message(e)`.

Подкласс пишет: `fields()` (какой код поля к какому элементу формы), `createTitle()`, `editTitle()`, `fill(...)`, `build()`, `save(...)`.

### 3.8. Окна справочников

**`ClientsController` + `clients-view.fxml`**

- Дополнительные фильтры: выпадающий список колл-центров и галочка «Только активные», кнопка «Сбросить». Реализованы через `extraFilter(...)` из базового класса.

**`CallCentersController` + `call-centers-view.fxml`**
- Столбцы: Название, Адрес, Статус (Работает/Не работает), Операторов.

**Формы:**
- `ClientFormController` + `client-form.fxml`: ФИО*, Телефон*, Email.
- `OperatorFormController` + `operator-form.fxml`: ФИО*, Логин*, Колл-центр* (выпадающий список только **работающих** колл-центров), галочка «Активен». Если оператор уже в неактивном колл-центре, этот колл-центр всё равно добавляется в список, чтобы не потерять привязку (тот же приём, что был в форме обращения для неактивного оператора).
- `CallCenterFormController` + `call-center-form.fxml`: Название*, Адрес*, галочка «Работает».

Звёздочка (*) в подписи означает обязательное поле.

### 3.9. `MainController.java` (изменён немного)

- Реализует `Refreshable`: `refresh()` просто вызывает существующий `reload()`.
- `reload()` теперь сохраняет выделенное обращение после перезагрузки.
- После сохранения формы, смены статуса и удаления вызывается `WindowFactory.refreshAll()` вместо `reload()`: тогда обновляются ещё и меню (счётчики) и окна клиентов/операторов (число обращений, нагрузка).

### 3.10. `AppContext.java` (изменён)

Добавлен `callCenters()`, чтобы контроллеры могли получить `CallCenterService`. Сервис уже создавался, но наружу не отдавался.

Стили плиток главного меню: `.nav-tile` (белая карточка со скруглением, при наведении синяя рамка), `.nav-title`, `.nav-caption`.

## 4. Слой сервисов (`service`): новые проверки

Раньше в справочниках проверялось только «поле не пустое», одним общим сообщением без подсветки. Теперь проверки как у обращений: у каждой ошибки есть **код поля**, и форма подсвечивает именно его.

### `ClientService`
- ФИО обязательно, до 150 символов.
- Телефон обязателен. Из него убираются пробелы, скобки и дефисы, потом проверка регулярным выражением `\+?\d{10,15}`: 10–15 цифр, можно с `+`. Ввели `+7 (999) 123-45-67`, сохранится `+79991234567`.
- Email необязателен. Если введён, проверяется по шаблону `что-то@что-то.что-то`. Пустой email сохраняется как `NULL`.
- Повтор телефона: в БД стоит `UNIQUE`, PostgreSQL возвращает ошибку с кодом SQLState `23505`. Сервис её ловит и бросает `BusinessException("phone", "клиент с таким номером уже есть")`.
- Удаление клиента, у которого есть обращения: в БД `ON DELETE RESTRICT`, код `23503`. Сервис превращает это в «Нельзя удалить клиента: у него есть обращения».

### `OperatorService`
- ФИО обязательно, логин обязателен и проверяется шаблоном `[A-Za-z0-9_.]{3,50}`.
- Колл-центр обязателен и должен существовать.
- **Переводить** в неактивный колл-центр нельзя. Но если оператор **уже** там, его можно редактировать (иначе нельзя было бы даже поправить опечатку в ФИО). Для этого `update` сравнивает старый и новый `callCenterId`.
- Занятый логин (`23505`) превращается в понятную ошибку у поля «Логин».
- Удаление: в БД у обращений `operator_id ... ON DELETE SET NULL`. Новые обращения просто становятся неназначенными. Но есть ограничение `CHECK working_requires_operator`: обращение в работе или завершённое обязано иметь оператора. Поэтому если у оператора такие есть, БД откажет (код `23514`), и сервис скажет: «Нельзя удалить оператора... снимите галочку «Активен»».

### `CallCenterService`
- Название (до 80 символов, уникально) и адрес (до 200) обязательны.
- Добавлен `getActive()` для выпадающего списка в форме оператора.
- Удаление колл-центра с операторами (`ON DELETE RESTRICT`, `23503`) даёт понятное сообщение.

### `AppealService` и `AppealRepository`
- `countByClient()`: сколько обращений у каждого клиента (`SELECT client_id, count(*) ... GROUP BY client_id`).
- `activeCountByOperator()`: сколько активных обращений у каждого оператора (одним запросом, а не по запросу на оператора).
- `maxActivePerOperator()`: отдаёт лимит 5, чтобы окно операторов показывало «N из 5», не дублируя число.

### `util/DbErrors.java`
Добавлены `isUniqueViolation`, `isForeignKeyViolation`, `isCheckViolation`. Это проверки SQLState `23505`, `23503`, `23514`, чтобы в сервисах не писать «магические» строки.

**Почему проверки в сервисе, а не в контроллере.** Контроллер отвечает только за интерфейс. Если завтра появится другой интерфейс (консоль из КР1, веб), правила останутся теми же. Плюс ограничения продублированы в БД (`UNIQUE`, `FOREIGN KEY`, `CHECK`): даже если кто-то обойдёт приложение, база некорректные данные не пропустит.

## 5. Тесты

Добавлен второй интеграционный тест `directoryWindowsRules()` в `CallCenterIntegrationTest`. Он проверяет на настоящей БД:

- неверный телефон, email и логин дают `BusinessException` с правильным кодом поля;
- телефон нормализуется (`+7 (123) 456...` → `+7123456...`), пустой email → `null`, пробелы в названии обрезаются;
- повтор телефона, логина, названия колл-центра даёт ошибку по полю;
- колл-центр с операторами не удаляется;
- оператора в неактивном колл-центре можно редактировать, а перевести в неактивный нельзя;
- клиента с обращениями удалить нельзя, счётчики `countByClient` и `activeCountByOperator` верные;
- оператора с обращением в работе удалить нельзя, а с новым обращением можно, и обращение становится неназначенным.

Результат прогона: **10 тестов, 0 ошибок** (4 логики, 4 экспорта и ошибок, 2 интеграционных на PostgreSQL 16).

## 6. База данных: скрипт миграции

Новый файл `database/migrate-to-call-centers.sql`. Нужен, только если база создана старым `init.sql`.

Что делает (внутри блока `DO $$ ... $$`, это анонимная процедура PostgreSQL):
1. Проверяет: есть `departments`, но нет `call_centers`? Если нет, пишет «переход не нужен» и ничего не делает, поэтому скрипт можно запускать повторно.
2. Переименовывает таблицу `departments` в `call_centers`.
3. Добавляет колонку `address`, заполняет её из старого `description` (у отделов адреса не было), пустые значения заменяет на «Адрес не указан», ставит `NOT NULL`, удаляет `description`.
4. Переименовывает у операторов `department_id` в `call_center_id`.

Все обращения, клиенты и операторы сохраняются. Проверено на копии старой схемы: после миграции приложение и все тесты работают.

Запуск (PowerShell, из папки проекта, контейнер должен быть запущен):

```powershell
Get-Content database/migrate-to-call-centers.sql | docker exec -i callcenter-pg psql -U postgres -d call_center
```

Если данные не жалко: `docker compose down -v; docker compose up -d --wait` пересоздаст базу с демо-данными из `init.sql`.

## 8. Вопросы на защите и ответы

**Как открывается отдельное окно в JavaFX?**
Создаётся новый `Stage`, в него ставится `Scene` с корнем, загруженным из FXML через `FXMLLoader`, и вызывается `show()`. У нас это `WindowFactory.openWindow`.

**Чем отличается `show()` от `showAndWait()`?**
`show()` показывает окно и сразу возвращает управление. `showAndWait()` ждёт, пока окно закроют; работает только для не главного окна. Формы открываются через `showAndWait()`, чтобы сразу после закрытия проверить, сохранили ли данные.

**Что такое модальность?**
`Modality.WINDOW_MODAL`: пока открыта форма, окно-владелец недоступно для кликов. Так пользователь не изменит таблицу, пока заполняет форму.

**Почему при повторном нажатии на плитку не открывается второе окно?**
`WindowFactory` хранит `Map<String, Stage>` открытых окон по имени FXML. Если окно уже есть, вызываются `toFront()` и `requestFocus()`.

**Как окна узнают, что данные изменились?**
Паттерн Observer: контроллеры реализуют `Refreshable` и регистрируются в `WindowFactory`. После любого сохранения/удаления вызывается `refreshAll()`, и каждое окно перечитывает данные из БД.

**Зачем абстрактные классы `EntityListController` и `EntityFormController`?**
Три окна и три формы почти одинаковые. Общее поведение написано один раз (принцип DRY), подкласс задаёт только отличия. Это наследование, абстрактные методы, generics и паттерн «Шаблонный метод».

**Как работает поиск в окнах справочников?**
`FilteredList` поверх `ObservableList` с данными. При вводе текста меняется предикат (`setPredicate`), и таблица показывает только подходящие строки. Запрос в БД при этом не делается.

**Почему сортировка по клику работает с `FilteredList`?**
Поверх `FilteredList` стоит `SortedList`, а его компаратор привязан к компаратору таблицы: `sorted.comparatorProperty().bind(table.comparatorProperty())`.

**Где проверяется, что телефон правильный?**
В `ClientService.validate`, регулярным выражением. Контроллер только передаёт текст из поля.

**Что будет, если ввести телефон, который уже есть?**
Сервис пытается сохранить, PostgreSQL отказывает по `UNIQUE` с SQLState `23505`, сервис ловит `SQLException` и бросает `BusinessException` с полем `phone`. Форма подсвечивает поле «Телефон».

**Почему нельзя удалить колл-центр с операторами?**
В БД `operators.call_center_id REFERENCES call_centers(id) ON DELETE RESTRICT`. Иначе операторы остались бы без колл-центра. Сервис переводит ошибку `23503` в понятный текст.

**Что происходит с обращениями при удалении оператора?**
`ON DELETE SET NULL`: новые обращения становятся неназначенными. Если есть обращения в работе или закрытые, удаление запрещено ограничением `CHECK working_requires_operator`, потому что им оператор обязателен. Вместо удаления оператора делают неактивным.

**Почему в форме оператора в списке только работающие колл-центры?**
Правило: нельзя назначить оператора в неактивный колл-центр. Список фильтрует это заранее, а сервис проверяет ещё раз, на случай обхода интерфейса.

**Зачем скрипт миграции, если есть `init.sql`?**
Docker выполняет `init.sql` только при первом создании volume. Если база уже была, её схему надо менять отдельно, `ALTER TABLE`, без потери данных.

**Как устроен `FXMLLoader` с наследованием контроллеров?**
Он ищет поля и методы с `@FXML` по всей иерархии классов, поэтому поля, объявленные в абстрактном родителе, тоже заполняются.

## 9. Честные ограничения (если спросят «а что можно улучшить»)

- Окна обновляются целиком при каждом изменении. Для учебного объёма данных это мгновенно, для большой базы стоило бы обновлять точечно или загружать данные в фоне (`javafx.concurrent.Task`).
- Поиск в справочниках работает в памяти, а не SQL-запросом с `WHERE`, как и у обращений.
- Миграция оставляет старые имена ограничений (`operators_department_id_fkey`). На работу это не влияет, только на название в `\d operators`.
