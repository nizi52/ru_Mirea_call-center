# Подготовка к защите проекта колл-центра

## Что делает программа

Приложение хранит клиентов, отделы, операторов и обращения в PostgreSQL. Через консоль можно создавать, просматривать, изменять и удалять записи всех четырёх сущностей. Для обращений есть поиск, фильтрация, сортировка, статистика и экспорт в Excel и CSV.

## Архитектура

Путь запроса: `Main` → сервис → репозиторий → JDBC → PostgreSQL. `Main` показывает меню и разбирает ввод. Сервис проверяет правила предметной области. Репозиторий исполняет SQL. Такое разделение позволяет менять способ хранения или интерфейс без переноса всей логики в один класс.

## Четыре сущности и связи

`Department` — отдел с названием и признаком активности. `Operator` — сотрудник с уникальным логином; `department_id` связывает его с отделом. `Client` — клиент с уникальным телефоном. `Appeal` — обращение с темой, категорией, статусом и датами; `client_id` обязателен, а `operator_id` может быть пустым у нового обращения. Один отдел содержит много операторов, один клиент может создать много обращений, один оператор может обрабатывать много обращений.

`PRIMARY KEY` однозначно определяет строку. `FOREIGN KEY` защищает связи: нельзя указать несуществующий отдел или клиент. `NOT NULL` запрещает пустое значение SQL `NULL`, `UNIQUE` не допускает повтор логина или телефона, `CHECK` ограничивает категорию и статус и проверяет дату закрытия. Проверки на уровне БД дополняют сервисные правила.

## ООП и коллекции

- **Инкапсуляция:** поля моделей объявлены `private`, доступ к ним предоставляют методы `get` и `set`. Объекты создаются через конструкторы.
- **Интерфейс:** `Repository<T, ID>` задаёт общие операции `findAll`, `findById`, `save`, `deleteById`.
- **Полиморфизм:** `OperatorRepository`, `ClientRepository`, `DepartmentRepository` и `AppealRepository` реализуют один интерфейс для разных типов. Сервис может хранить ссылку типа `Repository<Operator, Integer>` на объект `OperatorRepository`.
- **Enum:** `AppealStatus` содержит фиксированный набор статусов: `NEW`, `IN_PROGRESS`, `ESCALATED`, `RESOLVED`, `CLOSED`. Это безопаснее произвольных строк в Java-коде.
- **Коллекции:** `List<Appeal>` хранит считанные обращения; `Set` хранит допустимые категории; `Map` группирует статистику. `Stream API` используется в поиске, фильтрации, сортировке и расчётах.

## Бизнес-правила

Тема обращения обязательна. Указанный клиент и оператор должны существовать. Назначить новое обращение можно только активному оператору. Активных обращений со статусом `NEW`, `IN_PROGRESS` или `ESCALATED` у одного оператора может быть не больше пяти. Допустимые переходы: `NEW → IN_PROGRESS`, затем необязательно `ESCALATED`, затем `RESOLVED → CLOSED`. Переход в работу требует оператора. Закрытие без оператора запрещено, а `closed_at` ставится при закрытии и не может быть раньше `created_at`. Правила находятся в сервисах, поэтому действуют независимо от пункта меню.

## JDBC

JDBC — стандартный интерфейс Java для работы с SQL-базами. PostgreSQL JDBC Driver подключается через `pom.xml`. `DatabaseManager` создаёт `Connection`; репозитории используют `PreparedStatement` и читают `ResultSet`. `try-with-resources` закрывает соединение, запрос и результат даже при исключении.

`Statement` исполняет готовую строку SQL. `PreparedStatement` принимает SQL с `?`, а значения передаются методами вроде `setInt` и `setString`. Это отделяет данные от текста запроса, предотвращает SQL-инъекции и корректно обрабатывает кавычки в пользовательском вводе.

`SQLException` означает ошибку соединения или SQL-запроса. `BusinessException` сообщает о нарушении бизнес-правила, `EntityNotFoundException` — об отсутствующем ID. Меню перехватывает эти исключения, выводит понятное сообщение и продолжает работу.

## Поиск, статистика и экспорт

Поиск выполняется по имени/телефону клиента и частичному совпадению темы. Фильтры — по статусу и диапазону дат. Сортировки — по дате создания и статусу. Статистика включает число обращений, число по статусам, среднее время от создания до закрытия, нагрузку операторов, распределение категорий и оператора с наибольшей нагрузкой. Экспортёр получает уже подготовленный список обращений и записывает его в `.xlsx` через Apache POI или в `.csv` средствами Java.

## Что показать преподавателю

1. Открыть ER-диаграмму в `README.md` и показать четыре связанных таблицы в `database/init.sql`.
2. Запустить программу, вывести все таблицы и показать стартовые данные.
3. Создать клиента, затем обращение с его ID; показать связь в списке обращений.
4. Попробовать несуществующий ID и запретный переход `NEW → CLOSED` — программа должна показать ошибку и остаться в меню.
5. Показать поиск, фильтр, сортировку, статистику и два файла экспорта.

Для честного ответа на вопрос о проверке: автоматический интеграционный тест использует отдельную PostgreSQL-базу и проверяет реальный JDBC, CRUD, основные бизнес-правила, выборки, статистику и содержимое экспортированных файлов. Ограничение пяти активных обращений проверяется сервисом; при нескольких одновременных процессах без дополнительной блокировки базы возможна гонка назначений.
